Wellness Tourism Package Prediction: an MLOps pipeline for "Visit with Us"¶

Business problem. "Visit with Us" is launching a Wellness Tourism Package. Picking the right customers to call by hand is slow and inconsistent, so campaigns miss buyers and waste sales time.

Objective. Build an automated, repeatable pipeline that predicts whether a customer will buy the package, and serve the prediction in a web app. The pipeline lives in GitHub and covers data registration, cleaning, splitting, model tuning with experiment tracking, model commit, and app deployment, all driven by GitHub Actions.

Observations

  • There are no missing values, but the data is not clean: a stale index column, an ID column, a Fe Male spelling variant, and 117 hidden duplicate rows that only show up after the ID is ignored. Duplicates must be removed before splitting; otherwise the same customer can land in both the train and test sets and inflate the test scores.
  • The classes are imbalanced (about 1 in 5 buys), so we judge models on F1, recall and ROC-AUC, not accuracy.
  • Designation and ProductPitched are perfectly one-to-one (Executive = Basic, Manager = Deluxe, Senior Manager = Standard, AVP = Super Deluxe, VP = King). They carry the same information; tree models are not hurt by this, but it matters for the app, which warns on combinations never seen in training.
  • The few extreme values (a 127-minute pitch, a 1,000 income) are kept: tree-based models split on thresholds and are not thrown off by outliers.

What separates buyers from non-buyers

  • Age is a strong signal. Customers aged 25 or under buy at about 44%, against 11% for ages 35 to 40. Buyers have a median age of 32 versus 37 for non-buyers.
  • Passport holders buy at about 36%, against 12% without one. Passport ownership is a proxy for travel appetite.
  • Single customers buy at about 37%, versus 13 to 14% for married and divorced customers.
  • Basic (Executive) is the easiest product to sell at 30%; Super Deluxe (AVP) and King (VP) convert at 6% and 9%.
  • More follow-ups go with more purchases: 39% at six follow-ups versus 10 to 13% at one or two. This is association, not proof of cause, since salespeople may chase the customers who already look interested.
  • Pitch satisfaction score has only a weak simple link to buying (16% at score 1 versus 22% at score 5), and the income difference between buyers and non-buyers is small. A weak one-at-a-time link does not mean a feature is useless to a model, which can use it in combination with other fields (see the importance chart in section 4).

3. Data preparation¶

src/prepare_data.py loads the CSV straight from the repository data/ folder and applies the cleaning decisions from section 2:

  1. Drop Unnamed: 0 and CustomerID (no predictive information).
  2. Trim whitespace in text columns and correct Fe Male to Female.
  3. Drop rows with a missing target and exact duplicates.
  4. Create a stratified 80/20 train/test split with a fixed seed, so both parts keep the 19.3% purchase rate and the split is reproducible.
  5. Save train.csv and test.csv to data/processed/. In GitHub Actions this folder is uploaded as the prepared-data workflow artifact and downloaded by the model-building job.

Missing values are not filled here. Imputation lives inside the model pipeline (section 4), so it is learned from the training data only and also protects the deployed app from incomplete input.

4. Model building and experiment tracking¶

Approach

  • Preprocessing (inside the model pipeline, fitted on training data only): median imputation for numeric columns, most-frequent imputation and one-hot encoding for categorical columns. Unseen categories are ignored rather than crashing the app.
  • Six model families, as allowed by the brief: Decision Tree, Bagging, Random Forest, AdaBoost, Gradient Boosting and XGBoost. Class imbalance is handled with class weights (or scale_pos_weight for XGBoost) where the algorithm supports it.
  • Tuning: 20 randomized-search trials per model (fewer for AdaBoost, whose grid has only 16 combinations), scored by F1 with 5-fold stratified cross-validation. F1 balances catching buyers (recall) against wasting calls (precision).
  • Selection without peeking: the best model is chosen on cross-validated F1 over the training data only. The test set is used afterwards for reporting, so it cannot influence the choice.
  • Experiment tracking with MLflow: a parent run for the pipeline, one child run per model family, and one grandchild run for every parameter set tried, each logging its parameters and CV score. Test metrics are logged on the model runs.
  • Output: the winning pipeline (preprocessing plus estimator) is saved to models/best_model.joblib, alongside metrics.json and feature_schema.json. The GitHub Actions job commits these to the repository.

Which features does the model rely on?¶

Tree-based "impurity" importances over-credit noisy, many-valued columns, so we use permutation importance on the test set instead: shuffle one column, and measure how much the F1 score drops. A bigger drop means the model leans on that column more. Because the pipeline handles encoding, each original column is shuffled as a whole.

Sensitivity check: can the model work before the customer is contacted?¶

The business goal is to predict purchases before contacting a customer. But four columns only exist after a sales pitch has happened: ProductPitched, NumberOfFollowups, DurationOfPitch and PitchSatisfactionScore. The data dictionary lists them as inputs, so the deployed model uses them, but it is worth measuring how much of the score depends on them. Designation is a customer attribute and is kept (it already carries the same information as ProductPitched). We refit the same algorithm with the same parameters without the four pitch columns.

How far can we trust the test score? A near-duplicate check¶

Section 3 removed rows that were identical on every feature. But customers can also be nearly identical: the same person recorded twice with a small change, for example. If a test customer has such a "twin" in the training data, the model can score well by recognising the twin rather than by learning general patterns. We measure this: for each test customer, find the training customer who matches on the most of the 18 features, and count a near-twin as a match on 16 or more.

In [16]:
from sklearn.metrics import f1_score, precision_score, recall_score

train_values = train[FEATURES].to_numpy(dtype=object)
test_values = test[FEATURES].to_numpy(dtype=object)
matches = np.zeros((len(test_values), len(train_values)), dtype=np.int16)
for j in range(len(FEATURES)):
    matches += test_values[:, [j]] == train_values[:, j][None, :]      # columns on which the two customers agree

has_twin = matches.max(axis=1) >= 16
closest_label = train[TARGET].to_numpy()[matches.argmax(axis=1)]
twin_share = has_twin.mean()
twin_agree = (closest_label == y_test.to_numpy())[has_twin].mean()

def scores(mask):
    y, p = y_test.to_numpy()[mask], pred[mask]
    return {"customers": int(mask.sum()), "buyers": int(y.sum()), "precision": precision_score(y, p),
            "recall": recall_score(y, p), "f1": f1_score(y, p)}

twin_table = pd.DataFrame({
    "All test customers": scores(np.ones(len(y_test), dtype=bool)),
    "Has a near-twin in training data": scores(has_twin),
    "No near-twin (like a new customer)": scores(~has_twin),
}).T
twin_table[["customers", "buyers"]] = twin_table[["customers", "buyers"]].astype(int)
display(twin_table.round(3))

Reading the result. Customers with a near-twin are predicted almost perfectly, because the model has effectively seen them. Customers without a twin are the better stand-in for the real situation: a brand-new customer the sales team is about to call. On those, the scores are clearly lower than the headline numbers, so the realistic expectation is the bottom row, not the top row. The headline test score (and the cross-validation scores used to pick the model) are therefore optimistic. The model is still useful, but this is the figure to quote when judging how many buyers it will find. A stricter pipeline would group near-identical customers together before splitting; that is listed under next steps.

5. Model deployment (Streamlit)¶

The app (app.py) loads the model that the pipeline committed to models/, collects the customer and pitch details in a form, saves them into a one-row dataframe whose columns match the training data, and shows the predicted purchase probability. The sidebar shows which algorithm is deployed and its test metrics. Input choices come from models/feature_schema.json, which the training job regenerates, so the form stays consistent with the model.

The deployment dependencies are in requirements.txt, pinned to the exact versions used for training so the saved model loads identically in CI and in production. The app is hosted on Streamlit Community Cloud, which reads the repository on GitHub and redeploys automatically when the pipeline commits a new model.

6. MLOps pipeline (GitHub Actions)¶

.github/workflows/pipeline.yml automates the whole workflow. It runs on every push to main that changes the data, the pipeline code, the requirements or the workflow itself, and can also be started by hand (Run workflow).

Job Needs What it does
1. Register dataset none installs dependencies, runs validate_data.py: schema check plus summary
2. Prepare data job 1 runs prepare_data.py, uploads data/processed/ as the prepared-data artifact
3. Build and track model job 2 downloads the artifact, runs train_model.py (tuning plus MLflow), uploads the MLflow log as an artifact, then commits models/ to main as github-actions[bot]
4. Verify app job 3 fresh checkout of main, installs only the deployment requirements.txt, runs the app smoke test against the committed model

Design choices worth noting:

  • Jobs are chained with needs, so a failed validation stops everything downstream.
  • Data moves between jobs as a workflow artifact, because each job runs on a fresh machine.
  • The model is committed back to the repository only when it actually changed, and the push uses git pull --rebase first so a concurrent push to main does not break the run.
  • No infinite loop: commits pushed with the workflow's GITHUB_TOKEN do not trigger new workflow runs, and the trigger paths exclude models/ anyway.
  • Least privilege: the workflow is read-only by default; only the model job gets contents: write.
  • concurrency queues overlapping runs instead of letting them race to push.
  • The last job proves the deployed artifact works, using exactly the dependencies Streamlit Cloud installs.
  • Because each push to main that commits a new model also updates the repo Streamlit Cloud watches, the deployed app picks up the new model automatically.
